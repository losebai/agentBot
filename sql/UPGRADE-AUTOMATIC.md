# 启动数据库版本检测与自动升级

## 调用记录分类索引（0.6.2）

适用已具备完整统一归档表 `agent_bot_call_record` 的旧业务库。
备份并停止共享该库的旧实例后，启动清单在既有迁移之后执行
`call-record-classification.sql` / `call-record-classification.sqlite.sql`，
以 `call-record-classification-v1` 登记；同版本缺少流水时也执行。
完整新库已含相同生成列和索引，首次启动只核验结构并登记流水。

只新增虚拟生成列 `system_kind` 和联合索引 `idx_call_system_time`。
沿用原来的历史决策、指令识别规则和决策优先级，NULL 仍表示普通对话；
不改写正文、JSON、原类型、状态或密钥。索引保存分类结果，写入与更新自动维护，
分类计数无需逐行解析大 JSON；列表也可复用分类和时间索引。

首次建立索引会扫描既有归档，耗时与记录量、JSON 大小有关，需预留升级时间。
SQLite 原地增加虚拟列，不重建表，整个升级同一事务提交；
MySQL DDL 隐式提交，中断后按已有列和索引恢复，不重复 ADD。
手工执行 SQL 前须核对状态，两条增量语句不可盲目重复执行。
缺资源或结构不匹配时停止启动，不回退到无索引的 JSON 全表计数。

## 定时任务恢复租约（0.6.2）

适用已具备 `agent_bot_job_owner`、`agent_bot_job` 的完整旧业务库。
停止旧代码的所有实例并备份后，由启动清单在既有迁移之后执行
`job-recovery.sql` / `job-recovery.sqlite.sql`，登记 `job-recovery-v1`。
即使版本已为 0.6.2，缺少该迁移流水时仍执行；新库完整初始化脚本已含相同结构。

仅新增 `agent_bot_job_attempt` 及索引和外键，不修改任务、身份、密钥或历史结果。
未完成任务保留；旧 RUNNING 任务在原领取时间六分钟后可恢复，
新执行开始记录租约历史，不为升级前的执行补造记录。已有 FAILED 任务不自动复活。
正常退出可释放任务重新领取，硬中断须等租约到期；累计三次执行仍中断则停止恢复。
恢复不保证供应商侧请求幂等，可能产生重复模型费用。
MySQL DDL 可重入，SQLite 同一事务提交；升级失败停止启动，不扫描历史 SQL。

下面为通用升级机制及既有迁移说明。

正常启动 `agent-bot`、`chat` 或桌面后端时，在读取运行配置、装配插件和监听网络之前，
检查所选业务数据库的程序版本，并按 `database_upgrade.MIGRATIONS` 的明确顺序执行适用 SQL。
不会扫描并执行全部 SQL、归档脚本或重新运行完整初始化脚本。独立队列库不在本清单内。

新库使用对应后端的完整初始化脚本，其中包含版本表及迁移流水表；首次启动核验后登记版本。
同版本且迁移已完成时不重复执行增量 DDL。没有结构变化的软件版本只更新版本记录。

## 已有部署的首次版本登记

支持已完成 0.5.5 模型身份及记忆生命周期升级的 0.5.5、0.5.6、0.5.7 完整结构。
这些旧版没有数据库版本表，因此先核对实际表列及模型身份唯一索引，不用软件版本猜测库状态。
起点匹配后自动补齐 `startup-versioning.sql` / `startup-versioning.sqlite.sql`，
并执行 `bilibili-init.sql` / `bilibili-init.sqlite.sql`，保留已有配置、凭据、账号与业务数据。
已手工执行 B站增量的库可直接登记，不覆盖已有账号。

更旧或结构不完整的部署若缺少所需历史数据转换，会停止启动并提示缺少的结构。
请先完成原版本升级说明中的模型身份、会话及记忆数据迁移；不能为了通过检测而手填版本号。
当前版本不会自动执行 `sql/legacy/dispatch_chat_setting.sql` 等历史破坏性脚本。

## Agent 独立人格（0.5.10）

完成上述步骤后，以 `agent-personality-v1` 登记 `agent-personality.sql` /
`agent-personality.sqlite.sql`。适用起点包括已完成历史模型身份与记忆升级的完整
0.5.5–0.5.10 部署；即使版本表已是 0.5.10，缺少该迁移流水仍须执行。
无版本库只允许缺少新增 `personality_prompt`，不会放宽任何既有 Agent 字段的核验。

每个 Agent 新增独立人格，旧数据初始化为空字符串；`system_prompt` 原角色原样保留，
不会拆分、移动或改写旧角色、模型选择、工具权限、关联、配置、密钥及历史数据。
SQLite 新增 `TEXT NOT NULL DEFAULT ''`，在原子写事务中完成。
MySQL 为兼容不支持文本默认值的版本，最终为 `MEDIUMTEXT NOT NULL` 且不设置默认值；
先添加可空列，只为该新列的 NULL 回填空字符串，再收紧为非空。
完整新库使用同后端相同定义，MySQL 新建 Agent 由应用显式提供人格字符串。

启动升级器核验类型、可空性与默认值，完整新库或已手工完成的库只登记流水，
不会重复 `ADD COLUMN`；已完成的流水在每次启动仍核验该列最终定义。
MySQL 中断后重启按列状态跳过已提交的 ADD，恢复回填及非空约束，保留已有非空人格；
未知的同名列结构会停止启动。手工执行时应先检查列状态，再按上述顺序执行尚未完成步骤，
不能把这份含 ADD 的独立 SQL 当作可任意重复执行的脚本。

## 版本、校验和与失败

- `agent_bot_schema_version` 记录最终核验成功的程序版本；升级前后可查询该表核对。
- `agent_bot_schema_migration` 记录迁移 ID、版本、当前后端 SQL 的 SHA256、状态及完成时间。
  已执行脚本的内容或所属版本改变会阻止启动；后续变更必须新增迁移 ID。
- 数据库版本高于程序版本时拒绝启动，不自动降级；恢复旧版程序前需核对数据兼容性。
- 缺资源、锁不可用或执行失败时停止启动，不回退初始化、数据库后端或旧环境配置。
- SQLite 在同一个 `BEGIN IMMEDIATE` 写事务内升级、核验和更新版本，失败整体回滚。
- MySQL 使用专属连接命名锁保护完整过程；DDL 隐式提交，失败可能留下已完成结构。
  迁移流水保留失败状态且不推进版本。只有清单明确标记可重入的步骤允许重新启动重试；
  其他中断步骤须先修复或恢复备份，禁止盲目重放 SQL。

## 运维与新增迁移

升级会改变所选业务数据库。按正常发布流程保存一致备份，停止共享同一数据库的旧版实例。
命名锁只协调采用该机制的新实例，不会阻止未升级的旧程序访问业务表。

可显式运行 `agent-bot database upgrade` 提前完成与启动相同的升级并查看结果。
普通 `settings list` 等离线配置命令不执行迁移，也不启动机器人。

后续数据库结构变更须同步完整 MySQL / SQLite 初始化脚本、提供两种后端增量，
并在清单登记目标版本、唯一 ID、文件名与重入策略。文件显式加入 wheel / 源码包，
包检查和构建钩子在缺失时失败；不要修改已应用的历史增量。
