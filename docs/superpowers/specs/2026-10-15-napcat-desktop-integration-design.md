# Windows 桌面版 NapCat 托管集成设计

日期：2026-10-15。状态：方案方向已确认，本文待用户审阅；尚未实施代码。

## 目标与范围

用户已同意先完成“桌面托管、自动连接、打开官方登录页”。目标是 Windows x64 用户启动 AgentBot 后，在 NapCat 自带 WebUI 扫码即可连接 QQ，随后继续使用现有机器人、模型与 Agent 功能。

第一版支持托管 NapCat 和现有外部 NapCat 两种明确选择的模式。托管模式由桌面版启动与清理所属 NapCat；外部模式完全沿用现有正向或反向 OneBot 配置。命令行普通服务保持外部接入方式。

本次不实现内嵌二维码接口、多账号托管、NapCat 插件市场、后台常驻、自启动或自动更新。不改 QQ 消息协议、权限、任务队列、数据库结构及模型调用流程。

## 当前代码事实

- 实际 Python 源码已位于 `src/agent_bot/`，与仓库说明中的旧平铺描述不同。
- `desktop.py` 中桌面父进程通过私有标准输入管道管理后端；后端监听成功才通知所属窗口，关闭管道触发停机。
- `application.py` 通过公共运行时与插件管理器装配应用，QQ 是可禁用的 `qqbot` 插件。
- 管理接口已有 `/api/bots` 和运行状态；`Overview.tsx` 目前只能展示连接情况，不能观察 NapCat 进程和 WebUI。
- `StartupSettingsStore` 已提供环境覆盖判断、文件版本、跨进程锁及回滚，静态保存不会改变运行中的连接。
- Windows 安装器按白名单分发资源；构建脚本拒绝覆盖含运行数据的输出目录。
- 工作区存在其他未提交与已暂存修改，本次只新增本文，不整理或提交其他变更。

## 方案选择

采用桌面专用后端中的 NapCat supervisor：桌面父进程仍只管理其后端，后端在桌面启动路径中管理一个 NapCat 进程树。这样可以直接消费后端已经校验的有效启动配置，不需要通过日志或 HTTP 在父子进程之间传递 Token，也不会重复初始化数据库。

另一种方式是由桌面父进程直接启动两个独立子进程，但需要增加配置快照和秘密传输通道。把 NapCat 源码移入 Python 服务则无法消除 QQ 原生运行环境的依赖，且增加维护和分发成本。第一版均不采用。

```text
桌面父进程：原生菜单、打开登录页、所属后端生命周期
  └─ 桌面专用后端：公共运行时、QQ 插件、只读托管状态
      └─ NapCat supervisor
          └─ NapCat Shell 与独立 QQ 运行环境
              └─ OneBot V11 反向连接当前后端
```

## 用户使用流程

1. 带 NapCat 运行载荷的新安装在首次配置时启用托管模式；已有部署保持外部模式，不因升级自动启动第二个 QQ 实例。
2. 启动桌面窗口，后端先完成原有初始化和监听，再启动所属 NapCat。QQ 插件关闭时明确显示“QQ 插件未启用”，不启动 NapCat。
3. 首次使用通过原生“QQ → 打开 NapCat 登录页”进入独立的 WebUI 窗口。需要登录时使用 NapCat 自带的扫码和验证流程，主窗口继续提供管理功能。
4. NapCat 反向连接本后端后，运行概览显示实际 QQ 在线账号。用户仍需按现有规则配置允许的群、用户和模型。
5. 页面保存静态配置后继续使用当前进程；用户执行已有“服务 → 重启后端”时，后端和所属 NapCat 才按新配置重新启动。
6. 关闭 AgentBot 窗口，停止所属 NapCat 和后端。浏览器访问者关闭网页不影响服务。

原生 QQ 菜单提供托管模式选择、打开登录页和查看托管状态。模式选择使用固定选项，不提供任意命令执行；不增加 Token 菜单，也不向网页注入原生进程控制桥。

## 配置与数据归属

新增静态字段：

| 字段 | 定义 |
| --- | --- |
| `AGENT_BOT_NAPCAT_MODE` | `external` 或 `managed`；缺失按 `external`，首次全新安装有运行载荷时显式写入 `managed` |
| `AGENT_BOT_NAPCAT_WEBUI_PORT` | 托管 WebUI 端口，默认 6099，校验 1–65535 和占用；监听固定为本机回环 |

第一版托管目录固定在部署目录的 `data/napcat/`，不增加任意路径和命令配置。模式通过原生菜单写启动文件，使用 `StartupSettingsStore` 和当前 revision；环境覆盖时只读。网页本次不增加新的静态可写字段。

NapCat OneBot Token 使用后端本次启动的 `ONEBOT_V11_ACCESS_TOKEN`；不重新生成、不写数据库、不回填网页。会话密钥、管理员密码与 NapCat WebUI 密钥彼此独立。WebUI 密钥保存在 NapCat 自身配置，登录需要展示时仅由本机原生界面读取，不加入业务管理 API、状态文件或日志。

模式、启动参数在手动重启前保持旧快照。网页保存 Token 时不提前改写 NapCat；后端重启时才同步本次有效 Token。NapCat 配置通过原子替换更新，只改所属连接和 WebUI 字段，保留其他配置。

托管模式要求当前启动快照没有正向 OneBot 地址或 HTTP API 根地址；存在冲突则明确说明需清理这些字段并重启，不自动删除数据库配置。外部模式不改任何 NapCat 文件。

## 连接配置与首次登录

托管 NapCat 只启用名为 `agentbot-managed` 的所属反向连接，消息格式为 `array`。目标由后端实际监听成功的地址及端口构造，路径固定 `/onebot/v11/ws`；通配监听地址转换为对应 IPv4 或 IPv6 回环地址，IPv6 使用方括号。

运行载荷按一个已验证的 NapCat Shell 与 QQ 版本组合准备。集成代码使用该版本实际支持的默认 OneBot 配置模板，确保首次扫码完成后新账号继承连接设置；已存在的所属账号配置同步相同连接。不得假设写一个通用 JSON 后任意版本均能生效。

NapCat WebUI 的监听固定为回环，端口保存前探测占用；发现冲突不允许悄悄连接其他 WebUI。若上游运行时自动换端口，集成状态必须识别并报告端口不匹配，不能把原端口的响应认作就绪。

原生登录窗口打开当前所属实例的无密钥 WebUI URL，不把 Token 放进 URL、页面脚本或日志；需要时由原生提示显示本实例 WebUI 密钥。WebUI 的改密和二次验证流程由其自身负责。首次扫码成功不保证免除后续 QQ 风控验证。

## 进程生命周期与失败处理

- supervisor 只在 `--desktop-child` 路径装配；普通命令、模块导入和单元测试构造对象不启动 NapCat。
- 父窗口、后端和 NapCat 都通过显式所有权清理。Windows 使用 Job Object 约束所属后端及 NapCat 后代，避免启动脚本退出后 QQ 遗留；不得按进程名称终止系统中的 QQ。
- 启动脚本和参数来自随包固定清单，执行目录固定，隐藏控制台。QQ 登录数据必须通过所选运行载荷实际支持的独立路径保存，不能假设改变工作目录即可隔离 QQ 用户资料。
- 同一托管目录使用 OS 锁，第二个窗口明确报告“已有托管实例使用”，不接管旧进程、不创建第二个账号连接。
- 后端就绪后异步准备 NapCat；失败只标记托管状态，仍能进入管理页面。已明确选择托管而缺载荷、配置不兼容或端口冲突时不自动切换外部模式。
- 托管实例不做自动崩溃重启；错误保留清晰原因，由用户通过原生菜单重启后端重试。连接重连沿用该 NapCat 版本的既有行为。
- 正常关窗先取消尚未完成的 NapCat 启动，再停止 NapCat、完成后端正常 shutdown，最后释放 Job、管道和锁。超时终止也只作用于所属进程树。
- “修改端口”继续在停旧服务前完成范围和占用校验；成功保存后重启，新的 NapCat 连接使用新监听端口。NapCat 配置写入失败不影响后端管理功能，不回滚一个已经成功应用的后端端口。

## 只读状态与界面

supervisor 在应用内存维护状态，通过受现有管理认证保护的 `GET /api/napcat/status` 公开。没有桌面托管上下文时返回 `mode=external`，不探测或控制外部 NapCat。

响应只包含模式、进程状态、WebUI 就绪状态和固定错误码。进程状态限定为未启动、启动中、运行中、已停止、异常、QQ 插件未启用；不返回密钥、配置正文、任意文件路径或启动命令。

QQ 是否在线仍以插件管理器实际观察到的 `/api/bots` 为准。运行中且无连接显示“等待登录或连接”，不能把进程存活标成 QQ 在线，也不能仅凭没有连接断言需要扫码。

运行概览展示这些状态及“通过桌面 QQ 菜单打开登录页”的提示；不增加 HTTP 启停、重启、打开程序、写进程命令或任意 WebUI 代理接口。桌面父进程通过固定本地配置读取 WebUI 地址和必要密钥，网页不参与。

NapCat 日志写入 `logs/napcat.log`，只记录启动、退出、WebUI 就绪和固定错误码等解析后的允许事件，不保存上游原始输出。未知输出不落盘，不依赖替换已知 Token 来保证全部登录材料安全；界面错误仅使用固定文案。测试覆盖秘密不出现在任何日志与状态响应中。

## 运行载荷与安装发布

Windows 构建增加显式 NapCat 载荷输入。载荷清单必须提供 NapCat 版本、QQ 版本、文件 SHA256、固定启动入口以及独立资料和配置目录的启动约定；构建校验完整性，不下载浮动 `latest`，也不把安装引导器本身当成已经可运行的 QQ 环境。

发布包仅纳入经验证且允许分发的干净程序资源，放入 `runtime/napcat/`；首次启动按该版本约定创建 `data/napcat/` 下的配置与 QQ 用户资料。若运行载荷无法把可写配置从程序目录分离，则不能声明符合此设计，须先修订该载荷适配。

NapCat 源码、QQ 程序资源和第三方依赖各自保留来源及许可。正式捆绑前核对所选版本的分发权限；本文不是授权证明。未提供载荷的标准包继续支持外部模式；显式托管时缺载荷会报错。

安装器增加程序目录的白名单规则；构建输出检查识别干净载荷，禁止把 `data/napcat/`、QQ 登录资料、实际配置或日志打入包。更新只替换程序资源，不覆盖数据；卸载保留用户资料。保留既有 0.3.0 wheel，不改发布版本或上传任何安装包。

## 验收与验证

1. 使用假的 NapCat 启动器验证启动顺序、关窗取消、父进程异常退出和后代清理；不启动真实 QQ。
2. 验证已有安装默认外部模式、显式托管缺载荷报错、QQ 禁用不启动、重复实例不接管，以及普通 CLI 不托管。
3. 使用临时目录验证 Token 和端口仅在重启后同步、环境覆盖、文件版本冲突、写入失败、其他配置字节保留和日志脱敏。
4. 验证状态接口需要现有管理权限，不公开秘密，也不存在 HTTP 进程控制；界面区分进程运行和 QQ 在线。
5. 定向执行相关 Python 测试与 Ruff；界面变化后执行相关 Vitest、TypeScript 检查及一次前端构建。全部改动合并后才做 Windows 包与安装器验证。
6. 所选 NapCat/QQ 版本的真实扫码和 OneBot 联调独立列为手工发布验收，需使用用户提供的隔离测试账号；离线检查不冒充这一项已通过。
