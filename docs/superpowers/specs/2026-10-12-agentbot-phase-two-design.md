# agentBot 第二阶段：Python 普通 AI 服务

日期：2026-10-12

状态：用户于 2026-10-12 回复“继续”确认本设计；第二阶段已按确认的实施计划完成，验证结果与限制见 docs/migration/phase-two.md。

## 1. 目标与既有约束

继续已经确认的“Python 服务 + React/TypeScript 图形管理界面”迁移方向。在独立项目 `D:/items/web/agentBot` 内实现供应商、模型配置、普通同步和流式文本对话、会话记录，使明确选择 Python 的普通文本请求可以直接访问模型服务，无需调用 Java AI。

第一阶段已经迁入完整 Python Chat、管理 API、配置热刷新和浏览器界面。第二阶段复用这些能力及其 MySQL 连接池、运行时租约、请求预算和鉴权方式。保留单进程机器人运行方式。

沿用当前聊天顺序实施，不新建聊天、不委派子代理、不创建 Git 仓库、不提交或推送。旧 `dispatch-sdk`、`bai-web` 仅作只读参考。测试使用 Fake 数据库和 HTTP Mock，不调用真实模型、不连接 QQ、不修改生产数据。

## 2. 已核对的行为与迁移影响

| 来源 | 已确认行为 | 第二阶段处理 |
| --- | --- | --- |
| Java `ChatService.chatOne` | 无状态调用，调用者提供历史；成功结果包含 `replayContext`、模型、耗时和请求标识；保存失败仍返回付费结果 | Python 采用无状态请求，提供独立记录查询；记录失败单独报告 |
| Java `ChatRequestValidator` | 普通调用拒绝工具、Agent 参数；`input` 优先于 `messages`，最后才用 `prompt`；请求预算至多 300 秒 | 保留普通调用与工具调用的边界；本阶段 Python 仅接受文本，不能静默丢弃图片或工具 |
| Java `ChatProtocolPolicy` | `openai` 类型聊天地址必须以 `/v1/responses` 结束 | 明确使用 Responses 适配器，另设兼容 Chat Completions 协议 |
| Java `MainAgent.stream` | 无工具时为普通流，有工具或 MCP 时进入 Agent 流 | 本阶段只迁普通文本流，不将 Agent SSE 宣称为已迁移 |
| Java `DynamicModelConfig` | 按模型与供应商启用状态选择连接，可处理 `ownedBy/modelId` | Python 使用唯一公开模型别名与精确上游 ID，完整保留斜杠，不猜测或拼接模型名称 |
| Python `ChatClient` | 普通、Agent、多模态共用 `complete`，媒体另有入口 | 按本次请求能力选择实现，保留 Java 的未迁移能力 |
| Python `ModelGuard` | 调用之前读取 `ai_model(model_id,type,enabled)` | 校验必须识别能力及所选后端，不能用 Java 目录阻止 Python 模型，也不能放宽 Java 校验 |
| 第一阶段 `ChatProbe` | 固定普通文本、无工具，读取当前运行时模型和系统提示 | 复用为 Python 普通对话入口，保留原有 Java 同步模式 |

现有 Java 实体列出了 `anthropic` 类型，但目前检查到的模型目录适配器是 OpenAI 和 Ollama。该字段不构成本阶段已经支持 Anthropic 的证据。

## 3. 方案选择

采用方案 A：在同一服务内增加独立 AI 业务模块和显式路由适配器。普通 Python 请求直接调用业务模块，避免向自身发送 HTTP；管理界面沿用同源 `/api/v1` 接口。改动集中在既有客户端边界，后续 Agent 可以继续扩展。

方案 B 是另建 AI 进程，沿用 Java HTTP 地址布局。它方便跨进程部署，但本阶段会增加启动、鉴权、连接和运维配置，暂不采用。方案 C 是立即把整个 AI 客户端改为 Python；它要求同时迁移 Agent、媒体、任务和 Laya，超出第二阶段范围。

## 4. 能力路由与回退

增加数据库运行配置字段 `dispatch_chat_plain_ai_backend`，取值 `java` 或 `python`，默认 `java`。沿用配置 revision、热刷新和运行时租约；保存与应用状态继续分别显示。

| 请求能力 | 后端选择 |
| --- | --- |
| 管理界面的普通同步文本 | 依照 `dispatch_chat_plain_ai_backend` |
| QQ 普通文本、普通文本记忆压缩及回复整理 | 依照该字段；以最终有效的请求能力判断 |
| 管理界面的 Python 普通流式文本 | 仅在该字段为 `python` 时可用；Java 模式显示不可用说明 |
| Agent、联网工具、Chat 授权工具、MCP 或 Laya | 显式使用 Java 兼容实现 |
| 图片/视频理解、图片/音频生成、异步任务 | 显式使用 Java 兼容实现，待后续阶段迁移 |

普通 Python 路由要求无 Agent、无联网能力、无工具、无 MCP/Laya 能力、无图片或视频输入。分类由服务器结合有效配置和最终请求参数执行，不能让调用者自行标记绕过能力检查。未迁移能力走 Java 是预先定义的路由，不是 Python 失败后的自动回退。

模型预检同步识别上述分类。Python 请求从 Python 模型目录校验模型和供应商，Java 请求继续采用原有目录及 Java 权威校验。压缩等普通文本调用同样经过 Python 服务最终校验。业务预检与客户端实际路由使用同一个分类函数，防止判断不同。

Python 请求失败时返回其真实错误，不换模型、不切换协议、不尝试 Java，也不自动重发付费请求。回退操作是把该字段显式改回 `java`；Java 地址、凭据和模型兼容目录保留。切换期间已开始请求持有原运行时租约。

运行状态显示普通对话后端和各能力后端。不能用一个“全部 Python”标签遮蔽仍由 Java 提供的能力。

## 5. 模块与生命周期

新增 `src/agent_bot/ai/`，分为：

- `contracts`：类型化供应商、模型、文本请求、结果、用量和流式事件。
- `catalog`：供应商与模型存储、版本冲突处理、请求配置快照。
- `providers`：Responses、兼容 Chat Completions、Ollama 协议适配器及有限缓冲解析器。
- `service`：校验、配置解析、预算、调用、结果验证和记录。
- `sessions`：会话调用记录持久化与分页查询。
- `routing`：与现有 Chat 客户端、模型校验边界连接。

管理路由仍位于 `agent_bot/admin/`，应用装配负责注入依赖，不在模块导入时初始化 NoneBot、打开数据库或读取生产配置。避免重现第一阶段已经修复的插件包导入副作用。

AI 客户端归运行时快照管理，刷新和退出时关闭；数据库池继续由原生命周期所有者管理。供应商和模型每次请求生成一致快照，管理修改只影响后续调用，不能让正在流式输出的请求混用新地址或凭据。

## 6. 供应商与模型配置

使用独立新表，不修改 Java AI 表和第一阶段 `ai_model` 兼容目录：

| 表 | 核心数据 |
| --- | --- |
| `agent_bot_ai_provider` | ID、名称、协议、API 根地址、凭据环境变量引用、启用状态、描述、revision、时间 |
| `agent_bot_ai_model` | ID、唯一公开别名、精确上游模型 ID、供应商 ID、启用状态、revision、时间 |
| `agent_bot_ai_session` | 单次执行 ID、会话 ID、请求标识、配置模型和实际模型、状态、当前输入、回复、用量、耗时、记录时间 |

新供应商与模型默认禁用。模型别名用于 Chat 配置和界面选择，上游 ID 按配置原样发送，例如 `Qwen/Qwen3.5-9B` 不会被再次加前缀。只管理 `chat` 文本模型；不把图片模型登记为文本模型。

协议必须显式选择：

| 配置协议 | API 根地址示例 | 对话路径 |
| --- | --- | --- |
| `openai-responses` | `https://api.openai.com/v1` | `/responses` |
| `openai-chat` | `https://example.invalid/v1` | `/chat/completions` |
| `ollama` | `http://127.0.0.1:11434` | `/api/chat` |

配置字段定义为根地址，不接受完整对话路径以免重复拼接。旧 Java 模型 `baseUrl` 可能是完整端点，导入说明明确要求人工转换，不直接复制。管理员可配置本机或内网模型；拒绝非 HTTP(S)、URL 用户信息、query、fragment、控制字符和明显不合法地址。不跟随重定向，不接收任意请求头配置。

供应商只保存凭据引用，例如 `AGENT_BOT_PROVIDER_QWEN_KEY`。仅解析以 `AGENT_BOT_PROVIDER_` 为前缀的明确变量名，操作系统环境优先于本项目 `.env`，禁止变量插值。不读取旧目录密钥、不回传密钥值。允许明确配置无凭据的自托管端点；有引用但变量缺失时阻止调用。界面显示引用名和是否可用，实际凭据修改通过服务运行环境完成。

列表、新建、编辑、启用/禁用接口均要求管理员鉴权。编辑携带行级 `expected_revision`，冲突返回 409。删除仅允许已禁用且没有关联模型的供应商，以及已禁用的模型；会话记录保留当次名称快照。事务和参数化 SQL 保证引用与并发语义。

本阶段提供手动登记与编辑，不做上游模型列表同步、自动发现或旧库自动导入。文档给出旧配置到新字段的映射清单；生产密钥和会话数据另行迁移。

## 7. 普通对话协议

Python 服务内部使用类型化普通文本请求，携带模型别名、会话 ID、请求 ID、文本历史和可选采样参数。调用保持无状态，会话记录不会自动拼接进后续请求。

内部输入边界对齐 Java 普通文本验证：至多 100 条消息、单条文本至多 32000 字符、总文本至多 120000 字符；角色限于 system/user/assistant，存在有效用户内容，末条为 user；模型别名至多 200 字符，会话与请求 ID 至多 256 字符。管理界面仍采用第一阶段更小的 2000 字符当前输入和 12000 字符历史限制。

现有客户端边界将已构建的 `messages` 直接传给普通服务，避免再追加一次 `prompt`。若做旧请求归一化，遵循 `input > messages > prompt`，只接受文本内容；图片、视频、工具和 Agent 字段不能被忽略后当成普通请求。第一阶段系统提示保护继续适用于管理员对话。

继续采用 `LlmRequestOptions` 的校验范围，空值使用上游默认。各适配器只映射其支持的字段：Responses 的输出上限使用 `max_output_tokens`；Chat Completions 使用 `max_completion_tokens`；Ollama 使用 `options.num_predict`。温度、top-p 等按各协议映射；Ollama 的布尔思考设置映射到 `think`。不将 `enableThinking` 直接冒充 Responses 的 reasoning effort。非空但无法表达的参数返回 `AI_OPTION_UNSUPPORTED`，界面展示所选协议的参数支持说明；不得静默丢参数或发送任意扩展 JSON。

业务保留上游文本的换行与格式。空文本、仅思考内容、工具调用结果以及不符合普通文本契约的结果不当作成功回复。推理字段与回复分离，不注入 QQ 回复或普通聊天历史。token 用量缺失时为 null，不推算为 0。

错误至少区分模型不存在/禁用、供应商禁用、凭据缺失、参数不支持、鉴权拒绝、限流、超时、上游不可用、响应协议错误、目录/记录库不可用。管理 API 沿用类型化错误和服务器请求标识；机器人边界映射到已有不可用/拒绝/协议异常，保持队列处理语义。错误与日志不含密钥、完整请求、用户消息或上游原始错误体。

## 8. 流式输出与取消

新增管理员 `POST /api/v1/chat/stream`，通过带 Bearer 头的 fetch 读取 SSE，使用与同步管理对话相同的输入与模型选择。鉴权、输入和 Python 后端选择在响应开始前完成。

统一的 SSE 事件为 `start`、`delta`、`done`、`error`。每个事件包含请求标识；delta 仅包含新增回复文本，done 包含完成原因、实际模型、可选用量和记录保存状态。error 使用稳定错误分类。一个连接最多一个成功 done 或失败 error；错误之后不能再发送成功 done。

Responses 按事件类型解析文本 delta 和完成/失败事件；Chat Completions 解析 `choices[].delta` 与完成标识；Ollama 解析逐行 JSON 与 `done`。UTF-8、SSE 多行 data、CRLF、跨 HTTP 分块、空行与注释必须正确处理。单事件至多 256 KiB，累计正文至多 1 MiB；遇到超限、非法 JSON 或缺失完成信号返回协议错误，不能把断流误报成功。

目录查询、连接和模型输出共享至多 300 秒的请求预算，沿用更小的现有剩余预算，不通过持续收到小分块无限延长请求。HTTP 资源与并发调用数有界，不建立无限排队。

浏览器停止、退出管理或连接断开时取消本次上游请求并关闭流；保留已显示文本并标记取消，不添加成功历史。刷新配置等待该请求释放运行时租约。记录操作使用现有有界数据库池；已开始的数据库事务需要完成或回滚后才能释放池资源，不把线程取消宣称为数据库事务已终止。

原 `POST /api/v1/chat` 同步返回形状保持兼容，增加可选结果元数据时不破坏第一阶段客户端。Java 模式仍可同步调用；本阶段不给 Java 模式伪造流式体验。

不新增面向外部调用者的 Java HTTP 兼容端点；兼容发生在已存在的 Chat 客户端边界。Agent 的旧 SSE chunk 格式仍由 Java 处理。

## 9. 会话记录与保存失败

每次 Python 普通调用形成独立执行记录，区分 completed、failed、cancelled，不与 Chat 的 QQ 记忆表混用。保存当前用户输入、实际回复和调用元数据，不复制完整历史、原始上游响应、思考内容、密钥或工具令牌。失败/取消可保留已产生的回复并标明状态，不能参与成功对话续写。

在剩余预算内尽力保存记录。模型已经返回成功结果而数据库保存失败时，继续返回该结果，明确 `record_saved=false`，记录脱敏故障；不能诱导用户为了保存记录重新付费调用。流式同样通过 done 的保存状态表达。失败本身的记录保存失败不得掩盖原调用错误。

新增管理员分页查询及单次记录详情 API，支持会话 ID 和状态过滤，单页上限 100，按时间和执行 ID 稳定排序。列表不返回正文，详情按需加载输入和回复。所有查询鉴权，界面不从旧 Java 会话库混合展示数据。

暂不实现服务端自动历史续聊、搜索全部正文、文件导出和自动清理；部署文档说明记录包含聊天正文，保留策略由部署方管理。

## 10. 图形界面

保留运行概览、机器人配置和对话测试，加入供应商管理、模型管理、会话记录三个页面。

供应商页面显示协议、API 根地址、凭据引用、启用状态；模型页面显示公开别名、上游 ID、所属供应商和启用状态。编辑显示版本冲突，失败保留表单内容。不显示实际 API Key 输入或假连接成功状态。

对话页显示当前普通对话后端，Python 模式可选择已启用模型并切换同步/流式；临时选择不修改机器人全局配置。默认使用运行时 Chat 模型。流式支持停止，防止重复发送，将部分回复、完成、取消和错误区分显示。只有完整成功的一轮进入后续历史。

模型临时选择只作用于 Python 模式；Java 模式继续使用配置模型，避免把 Python 模型 ID 发给 Java。后端根据所选模式验证此限制。

会话记录页展示实际状态、模型、耗时、用量和请求标识，详情按需查看正文。页面切换保留正在进行的聊天；退出时清除管理员 token 并取消请求。更新界面阶段标识，删除只适用于第一阶段的 Java 固定说明。

## 11. 数据库升级与回退

提供仅含新表的幂等 SQL 初始化脚本，不包含 DROP，不升级或复用旧 Java AI 表。新模块运行前校验自身表结构，给出明确初始化错误，不用内存存储掩盖缺表。

默认 Java 配置下，未初始化 Python 表不能破坏原机器人启动与原同步对话；Python 管理功能返回明确未初始化状态。选择 Python 后，缺表、目录无模型或凭据不可用体现在 Python 就绪状态和实际请求错误中。服务存活、机器人基础就绪、Python AI 配置就绪分别可观察，不自动探测真实付费模型。

回退为显式切回 Java，保留新表便于以后恢复。第二阶段构建发布版本为 0.2.0；切换旧二进制时需要先把数据库运行配置恢复为第一阶段可识别的字段集合，并保留备份，不能承诺未知配置字段一定被旧版本接受。提供无生产操作的回退说明及演练测试。

## 12. 验证与验收

新增行为测试覆盖三种协议的同步与真实增量解析、模型精确选择、启用状态、凭据引用、采样参数映射、上游错误脱敏、总超时、分块上限、流中失败、取消资源释放及保存失败后结果保留。

管理测试覆盖鉴权、秘密不回传、行版本冲突、引用约束、分页与详情。路由契约测试明确断言 Python 普通请求不访问 Java，工具/多模态/媒体请求仍走 Java，Python 故障不回退。覆盖热刷新租约与初始导入无副作用。

前端测试覆盖供应商/模型编辑冲突、流式成功与停止、取消后历史、保存警告、后端模式限制和会话详情。完成 TypeScript、测试、生产构建及浏览器检查。

运行第一阶段完整离线回归、Ruff、至少 80% 分支覆盖率、依赖锁一致性、wheel/sdist 构建和独立安装资源检查。保留已明确排除的真实 MySQL 破坏性测试，不扩大为真实外部联调。迁移报告提供实际测试数量与结果，不能把 Mock 通过宣称为真实模型联调成功。

验收要求：图形界面能够配置并选择 Python 模型；同步和流式接口在 Mock 下确实直接执行供应商协议；结果与会话记录一致且故障诚实可见；未迁移能力保留明确定义的 Java 路由；旧项目及本地修改完整保留。
