# agentBot 第三阶段：Python Agent、Skill 与 MCP

日期：2026-10-12。状态：用户已确认设计与计划，第三阶段已实现并完成离线回归；交付细节见第三阶段迁移记录。

## 1. 目标与既有约束

在第二阶段 0.2.0 的 Python 服务与 React 管理界面中，实现真正的多轮工具调用 Agent。GUI 与 QQ 使用同一个执行内核，能够选择模型和技能、调用已授权的工具、继续推理并给出最终答复。执行步骤可观察、可取消、可追溯。

本阶段按既定路线迁移 Agent、Skill、MCP 客户端、工具授权与执行循环。保留旧 Java 项目及其已有修改；仅写入 agentBot。沿用独立目录，不初始化 Git、不提交、不推送、不创建聊天或子代理。开发验证使用隔离数据库替身、HTTP Mock 和本地协议服务，不连接真实 QQ、付费模型或生产 MCP。

媒体、后台任务、Laya、soloncode、动态 Java/Lua 执行属于第四阶段。第三阶段不能以请求仍转发 Java 的方式宣称完成 Python Agent。

## 2. 源码核对结果

本设计依据以下现有边界，而非假设旧 Agent 仅有一次模型调用：

| 来源 | 必须理解并保留的语义 |
| --- | --- |
| Java `MainAgent` | Agent 预设、模型选择、工具与 MCP 装配、流式执行 |
| Java `ChatAgentService` | Chat 工具令牌、请求总预算、最终回复要求、工具错误不能冒充成功 |
| Java `AgentTurnBudgetInterceptor` | 1–5 个工具轮次，额外一次禁止调用工具的最终回答 |
| Java `AgentSystemPromptBuilder` | Skill 是提示词和工具依赖声明，不授予工具权限；工具结果属于不可信资料 |
| Java `AiMcpClientFactory` / `AiMcpToolService` | 已登记的 HTTP 服务、streamable/sse、白名单、名称冲突、请求结束释放资源 |
| Java `McpWebSearchGateway` / `WebSearchTool` | 稳定名称 `web_search`，搜索类 MCP 封装、查询和结果上限 |
| Python `ToolSessionStore` / `ChatToolRegistry` / `ChatMcpServer` | 请求级授权、用户/群/会话作用域、严格参数校验、令牌撤销与截止时间 |
| Python `RoutingAiClient` / `RoutedModelGuard` | 显式能力路由、准确模型目录预检、错误分类、无故障回退 |
| Python `ManagedStreamingResponse` | 浏览器断开时在原发送任务中关闭生成器并释放运行时租约 |

旧实现中 Agent 的 `skillIds` 字段存在，但 `MainAgent` 实际注入全部启用技能；不能把字段存在当作按 Agent 选择技能已经实现。新实现明确采用关联技能，列入兼容性变化。

## 3. 方案选择

推荐方案 A：在同一服务内新增 `agent_bot.agent` 模块，扩展已有供应商协议适配器，复用 Chat 工具服务和现有生命周期。优点是授权上下文与取消能贯通，部署仍是单服务，Java 边界可逐项切换；成本是需要明确实现和测试 Agent 循环。

方案 B：引入独立 Agent 框架。可以减少部分循环代码，但会新增消息、记忆、工具与取消语义的适配面，需要重新验证现有三种供应商协议及 QQ 权限。

方案 C：新增独立 Python Agent 服务。便于分开扩容，但需要跨服务传递授权与取消、额外部署和配置。当前目标不需要增加这些运行组件。

本草案采用 A。

## 4. 能力范围与路由

新增独立运行配置 `dispatch_chat_agent_backend=java|python`，默认 `java`，普通文本仍由 `dispatch_chat_plain_ai_backend` 控制。新增可空的 `dispatch_chat_python_agent_code`，绑定 Python Agent 预设；为空时使用当前 Chat 模型、系统提示词、轮次和请求声明，仍经过统一授权。

按有效请求能力选择后端，模型预检与真正调用必须使用同一个路由结果：

| 请求 | 本阶段行为 |
| --- | --- |
| 无工具的普通文本 | 第二阶段普通后端 |
| 文本 Agent、联网、第三阶段 Chat 工具、通用 MCP | 由 Agent 后端配置决定 |
| 图片/视频输入、Laya 服务或决策 | 整个请求明确走 Java |
| job、soloncode、绘图工作流、TTS 等第四阶段工具 | 若本次授权工具集合包含这些能力，整个 QQ 请求走 Java |
| GUI 显式选择 Python Agent 却要求未迁移能力 | 执行前明确拒绝，界面说明未迁移能力 |

不根据 Python 调用失败自动切换 Java，不执行到一半再切换。概览和请求记录显示实际后端及路由原因。默认启用的第四阶段工具可能让 QQ 请求继续使用 Java，启用文档必须解释如何选择仅含已迁移能力的授权集合。

第三阶段 Chat 工具集合为 `memory`、`naraka_query`、`naraka_search`、`mention_member`；复用现有业务实现与作用域，不重新实现 QQ 发送。`mention_member` 保持登记最终回复 @ 目标的语义，最终消息仍由网关统一发送。

联网工具迁移 `web_search` 和 `read_url`。其他旧内置工具（例如客户端 IP 和抖音媒体解析）不纳入本阶段 Python 工具目录，不伪造返回值。

## 5. 数据与模块边界

新增 `agent_bot.agent` 下的 contracts、catalog、prompting、engine、tools、mcp、records 模块；HTTP/数据库细节不放进循环或管理路由。复用第二阶段数据库池、模型目录、凭据解析模式、请求预算及安全错误结构。

新增独立 SQL 脚本，使用 `agent_bot_agent`、`agent_bot_skill`、`agent_bot_mcp`、`agent_bot_agent_skill`、`agent_bot_agent_mcp`、`agent_bot_agent_run`、`agent_bot_agent_step` 表。Agent 与模型使用数据库关联；MCP/Skill 关联用关系表，工具名称列表使用有界 JSON。所有目录对象默认禁用，更新使用 revision CAS，支持分页、启用/禁用和引用删除约束。SQL 不删除旧表、不自动导入旧数据。

- Agent：稳定 code、名称、描述、系统提示词、模型、Skill 关联、允许工具、MCP 关联、max_steps、采样选项、启用状态、revision 和时间。
- Skill：名称、描述、分类、提示词、示例、声明依赖工具、启用状态、revision 和时间。仅注入所选 Agent 关联且启用的技能，稳定排序；禁用或缺失依赖在运行准备阶段给出明确错误。技能内容不当作 Python、Shell 或文件执行。
- MCP：稳定 code、名称、描述、general/search 分类、streamable/sse 传输、endpoint、可选凭据引用、allowed_tools、search_tool、单次超时、required 标记、启用状态与 revision。凭据只保存 `AGENT_BOT_MCP_` 环境变量引用，不保存实际值。
- Run：execution_id、请求/会话标识、入口类型、实际模型和后端、目录 revision 快照、状态、耗时、用量、当前用户正文与最终/部分答复、脱敏错误码。
- Step：run_id、有序序号、轮次、类型、工具名、调用 ID、状态、耗时、受限结果摘要。默认不持久化原始工具参数、完整远端返回、记忆正文、系统提示词或令牌。

运行状态为 running/completed/failed/cancelled；进程异常留下的 running 记录展示为“未确认结束”，不能伪造成功或自动重跑。无跨进程续跑承诺。

模型、Agent、Skill、MCP 在执行前读取一致的配置快照；运行中的请求不混入编辑后的 endpoint、工具或提示词。热刷新继续沿用运行时租约。新表缺失只阻止 Python Agent 操作，不能破坏默认 Java 或第二阶段普通对话。

## 6. Agent 执行与供应商协议

工具调用使用独立的类型化消息契约：模型文本、完整工具调用、工具结果、用量与终态。普通 `TextRequest` 的公开语义保持不变，不能把 JSON 字符串塞进普通回答再用正则猜工具调用。

为现有 Responses、兼容 Chat Completions、Ollama 三类适配器增加工具消息往返能力，分别保留其原生 call ID、函数名、参数和结果关联。供应商能力不同的地方显式拒绝不支持的选项。实现前核对当前锁定依赖与协议官方资料，不依赖猜测。

执行顺序：验证请求和目录 → 获取并发名额 → 固定快照与总截止时间 → 获取本次授权工具 → 模型调用 → 校验完整工具调用 → 顺序执行工具并回传结果 → 下一轮 → 最终回答 → 收尾、关闭资源和记录。

服务器硬上限：同时最多 8 个 Agent 请求，不建立无限等待队列；工具轮次默认 3、可配 1–5；每轮最多 8 次工具调用，总计最多 40 次；总预算不超过 300 秒且继承调用者更短预算。工具轮次耗尽时增加一次无工具收尾模型调用，预算不重置。收尾仍请求工具、返回空正文或异常终态都视为失败。

一轮模型同时返回文本与工具调用时，文本属于中间内容，不提前发送为最终答复。工具按返回次序串行执行，避免有副作用的调用相互竞争。模型生成参数必须在全部片段组装和校验后才可执行；重复 call ID、重名工具、未知工具、非法 JSON、无效参数均不得产生工具副作用。

工具业务错误可以以类型化失败结果供模型处理；授权失败、预算耗尽、协议损坏和取消直接终止。连接或调用不做自动重试。有副作用的操作在取消前可能已经完成，记录必须区分已完成和未确认，停止按钮不能承诺回滚。

输入沿用 100 条消息、单条 32,000 字符、总输入 120,000 字符限制；角色提示词不超过 32,000 字符，单 Skill 不超过 16,000，组装系统提示词不超过 65,536。工具参数单次最多 64 KiB，结果最多 32,000 字符，模型正文最多 1 MiB，流式帧最多 256 KiB。累计上下文达到限制明确终止，不任意丢弃工具结果而破坏 call ID 对应关系。

模型内部推理内容不写入事件、日志或界面。步骤展示可观察的模型调用状态、工具名、结果状态与耗时。

## 7. 权限与 Chat 工具复用

可执行工具是服务端启用能力、Agent 允许集合、本次请求选择和入口授权的交集。省略请求工具字段使用预设允许集合；显式空列表代表禁用工具。Skill 依赖只检查是否可用，不扩大集合。普通用户文本和模型输出均不能增加权限。

QQ 本地工具通过请求现有的 ToolSessionStore 和 Chat 工具边界调用，每次调用再次检查令牌、截止时间、作用域和允许集合。复用 ChatMcpServer 的业务适配或抽出的共享调用边界，避免服务向自己发送 HTTP。令牌只在执行内存中传递，不进入模型消息、持久化记录或流式事件。

GUI 管理员登录不自动拥有某个 QQ 用户/群的工具会话；GUI 可以测试联网和所选 MCP 工具，但不允许传入任意 bot/group/user 字段伪造 Chat 授权。需要 QQ 上下文的工具只在真实网关授权流程或隔离测试中运行。

与旧实现工具列表合并行为的差异必须写入迁移记录：新实现不允许请求参数突破 Agent 允许集合；预设缺失或禁用直接失败，不忽略 agent code 并继续执行。

## 8. MCP、搜索与网页读取

使用已安装且锁定的 MCP SDK，支持 Streamable HTTP 与旧 SSE；不增加 stdio/任意命令执行。模型请求只能选择已登记服务 code，不能提交 endpoint、headers、凭据或客户端配置。

HTTP(S) endpoint 禁止用户信息、查询、片段和控制字符。管理员登记的 MCP 可以使用内网地址以连接本地服务；这不授予 `read_url` 访问内网的能力。凭据只用于所登记服务，不跟随跨源重定向，不泄漏给 SSE 广告的异源消息端点。

一次最多选择 3 个通用服务，远端可调用工具总计最多 20 个。`allowed_tools` 必须非空，显式 `*` 才代表本次发现集合；通配符不取消数量上限或 Agent 权限约束。初始化最多 10 秒，单次调用配置 1–30 秒，全部受请求剩余预算约束。发现分页限制为 10 页，循环游标或超限失败。

本地与远端名称冲突直接拒绝，不自动重命名。校验输入 schema、参数对象及工具返回：schema 至多 64 KiB、嵌套深度 16，禁止需要网络获取的引用；仅执行受支持并验证过的 JSON Schema，不删除约束来假装兼容。远端非文本/非结构化 JSON 内容给出不支持结果，不在第三阶段内下载图片或音频。

沿用旧通用 MCP 可选连接语义，但让管理员可见：required=false 时只有连接失败可以跳过，并记录 service_unavailable 警告；required=true 时终止。配置错误、认证错误、工具冲突、无效 schema 和请求截止不跳过。没有自动发现替代服务器或重新执行工具。

`web_search` 使用登记的 search 类 MCP，经固定的 search_tool 适配；保留现有 Open-WebSearch 和 `searxng_web_search` 参数/返回映射。查询最多 300 字符、结果最多 5 项、上下文最多 10,000 字符，仅保留合法 HTTP(S) 来源 URL；搜索类服务不能当作 general MCP 绕开搜索约束。新增运行配置选择一个搜索服务 code，默认空，未配置时明确不可用。

`read_url` 保留旧参数语义并在 Python 中实际读取公开网页。仅接受公开 HTTP(S)，验证 DNS 所有地址、实际连接目标和每次重定向，拒绝 loopback/private/link-local 等内部目的地；不携带 MCP 或模型凭据。请求总预算、最多 3 次重定向、解压后最多 1 MiB、输出最多 32,000 字符；不执行 JavaScript。外部文本进入工具结果而非系统指令。

请求成功、错误、取消、浏览器断开时，MCP 会话与传输必须在创建任务的上下文内有界关闭；沿用第二阶段已验证的流式资源释放方式，不依靠垃圾回收。

## 9. 管理 API、执行记录与 GUI

沿用 `/api/v1` 和管理员 Bearer 鉴权。新增 `/agents`、`/skills`、`/mcp-servers` 的列表/详情/创建/部分更新/删除；分页上限 100，revision 冲突返回 409 且界面保留未保存输入。返回凭据引用与可用布尔值，不返回密钥。

新增 `/agent-runs`（同步 POST、记录列表 GET）、`/agent-runs/stream`（POST SSE）、`/agent-runs/{execution_id}`（详情含分页步骤）。GUI 请求包含 agent_code、prompt/messages、session_id、request_id 和可收紧的轮次/预算；不接受调用者填写工具执行结果、Chat 工具令牌或运行状态。相同 request_id 只是关联标识，不承诺重试幂等；失败后界面不能自动重新发起。

流式事件为 start、model_start、tool_start、tool_result、warning、text_delta、done、error，具有 execution_id 与递增序号。done/error 互斥且唯一；中途 EOF 是失败。最终文本使用真正供应商流式输出，不用计时器切分完整回复模拟。工具参数碎片不显示为完整调用，UI 不显示内部推理。

停止生成通过 AbortController 断开执行流，服务端取消当前模型/工具并尽力保存 cancelled 记录。退出管理或卸载执行页面必须停止请求。同步与流式共用同一内核，不维护两套循环。记录失败要告知 record_saved=false，不能把已经得到的成功结果变成用户重试造成的重复工具调用。

新增 Agent、技能、MCP 管理页；对话测试增加“普通/Agent”模式、Agent 选择、真实工具步骤和停止状态；会话记录区分普通记录与 Agent 执行详情。概览显示普通、Agent、媒体分别使用的后端和本地初始化状态。工具结果默认展示受限摘要，明确成功/失败/取消，不把 queued 或中间文本展示为最终成功。

## 10. 验证与交付标准

1. 三种模型协议均覆盖完整工具往返、多工具、分块参数、工具错误、空回复和收尾禁用工具；验证发出的实际 HTTP 请求内容。
2. Agent 循环覆盖 1/3/5 轮边界、最终收尾、未知工具、重复 ID、参数上限、模型篡改授权、总预算递减与超限并发。
3. Chat 权限覆盖令牌缺失/失效/撤销、跨用户/群/会话、调用前再次校验、memory 和 mention 副作用语义；模型不接触令牌。
4. MCP 覆盖两种传输、本地真实协议握手与工具往返、发现分页、允许集合、冲突、schema、可选服务警告、认证和跨源端点、超限响应、取消释放。
5. 搜索与网页读取使用 HTTP/DNS 替身，覆盖结果裁剪、失败、非法 URL、重定向内网及连接目标校验；不连接真实网站。
6. API 覆盖鉴权、CRUD/CAS、引用约束、缺表、同步/流式、错误脱敏和记录；用真实 ASGI 断开测试确认工具关闭、租约释放、没有成功 done。
7. 路由回归覆盖普通/Agent/第四阶段混合请求，确认模型预检一致、显式回退可用、Python 故障不会转 Java。
8. 前端验证目录编辑、冲突保留、步骤事件、停止、退出、历史只接受成功轮次；完成 TypeScript、Vitest、生产构建和桌面/手机实际浏览器检查。
9. 最终执行根 AGENTS.md 指定离线回归与 Ruff，保留 80% 分支覆盖率门槛和真实数据库破坏性测试排除项。
10. 发布版本目标 0.3.0：wheel/sdist 包含新 SQL 与 GUI，在独立环境安装、导入及 CLI 验证；更新来源清单、README、第三阶段迁移记录和回退演练。

离线通过不能宣称真实 MySQL 锁/DDL、QQ 或生产模型/MCP 联调完成。最终报告分别列出已实现能力、实际验证和外部联调范围。

## 11. 启用、兼容性和回退

用户先在独立库显式导入新增 SQL，登记模型、技能、Agent 和 MCP，配置环境凭据，在 GUI 验证后再切换 Agent 后端。默认配置继续使用 Java，普通后端独立设置。

回退时将 Agent 后端设为 java，恢复 Java 中存在的模型标识和 MCP code，等待配置应用。回退 0.2.0 二进制前通过既有 SettingsStore revision 流程移除第三阶段新增配置字段，保留新增目录和记录表，不执行 DROP。轮次及搜索服务选择等新增字段须在实现计划中逐项列出并纳入回退测试。

旧目录数据不自动复制；技能关联与权限交集是显式行为变化。角色提示词仍由运行配置/管理员维护，不把仓库 AGENTS.md 当作机器人角色。

## 12. 审阅结论

本阶段是一条闭环迁移：目录配置 → 授权 → 模型工具循环 → MCP/Chat 工具 → GUI/QQ 接入 → 记录与取消。详细实施计划应按这些依赖拆成可验证任务，在本设计审阅后编写。

自检：已明确迁移边界、Java 路由条件、Skill 与权限差异、错误与取消、资源上限、验证与回退。此处保留已确认的设计范围；实现与验证证据以第三阶段迁移记录为准。
